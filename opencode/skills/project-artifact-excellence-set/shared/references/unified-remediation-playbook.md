# Unified Remediation Playbook

This is the canonical cross-skill remediation reference for project artifacts and skill/agent packages. The former `project-artifact-auditor/references/remediation-patterns.md` and `skills-create-excellence/references/remediation.md` point here so that policy and examples do not drift. Apply only the patterns relevant to the actual evidence; do not force an issue into a pattern that does not fit.

## Standard Remediation Protocol
1. **Preserve evidence:** record stable finding ID, exact artifact/location, observed state, expected state, severity, confidence, date, and source. Separate verified facts from inference and unknowns.
2. **Triage:** use Critical / Major / Minor / Suggestion severity against user harm, security/compliance exposure, reliability, downstream rework, cost, and delivery impact. Escalate Critical immediately. Do not downgrade uncertainty into a factual assertion.
3. **Identify the failure layer:** project requirement/design/implementation/operations; user/human factors; skill trigger/instruction/reference/contract/validation; or cross-cutting. Distinguish project defect from a suspected weakness in the skill used to audit or produce it.
4. **Find the root cause:** state why the defect escaped, what assumptions or controls failed, and which downstream artifacts or user journeys are affected.
5. **Choose a smallest-effective change:** name the owner, dependency, scope, rollback/recovery path, and effort. Do not broaden product scope silently.
6. **Make acceptance observable:** define a pass/fail criterion, test/data source, measurement window, and baseline where relevant. Use appropriate technical E2E checks and human-factors checks.
7. **Verify the fix:** reproduce the old failure, apply the change, run regression and cross-artifact checks, inspect user impact, and retain evidence. A code/document edit alone is not proof of resolution.
8. **Close with residual risk:** record validation result, reviewer, unresolved risk, and whether the pattern should be added to a shared reference or test fixture.

## Pattern-to-Action Matrix

| Failure family / signal | Typical root-cause question | Remediation actions | Acceptance / verification evidence | Escalation guidance |
|---|---|---|---|---|
| Ambiguous requirement or user story | Can two reasonable readers implement different outcomes? | Rewrite actor, intent, constraints, edge cases, and observable acceptance criteria; identify out-of-scope behavior. | Independent reviewers agree on interpretation; criteria pass/fail without unstated assumptions. | Major when ambiguity affects critical path, compliance, or repeated rework. |
| Missing acceptance criteria | Is there a user-observable test for the promised behavior? | Add success, error, boundary, recovery, and accessibility conditions to each major requirement. | Requirement-to-test mapping and test evidence exist. | Major when core user journeys are unverifiable. |
| Missing or vague non-functional requirement | Which quality attribute is at risk, under what load/context, and how will it be verified? | Define scenario, measure, target, data source, environment, and test method for performance, security, reliability, accessibility, maintainability, or cost. | Threshold has rationale and a reproducible verification method. | Critical/Major according to harm/exposure and criticality. |
| Broken traceability or orphan artifact | Which requirement, design decision, test, or operational signal is missing? | Assign stable IDs; map requirement ↔ design ↔ tests ↔ runtime signals; record legitimate non-requirements. | Bidirectional traceability report has no unexplained critical-path orphan. | Major when release-critical capability is unverified. |
| Contradictory documents or interface contracts | Which source is authoritative and which consumers depend on the old contract? | Resolve source of truth; update schemas, examples, compatibility/version policy, consumers, and migration notes. | Contract tests and cross-artifact consistency checks pass. | Critical if contradiction can corrupt data, break auth, or cause data loss. |
| Weak architecture / reliability / security coverage | What fails under dependency, load, privilege, or recovery loss? | Add threat/failure model, trust boundaries, dependency map, SLO/SLI, rollback/recovery, alert ownership, and tested runbooks. | Threat scenarios and critical failure/recovery tests are evidenced. | Escalate immediately for material security/safety/data-loss exposure. |
| E2E performance or delivery regression | Which user journey and deployment change correlate with regression? | Segment by journey, environment/device, release, and user class; define baseline and p75/p95/p99 as appropriate; use Core Web Vitals only for LCP/INP/CLS, and label TTFB/FCP/TBT as supporting diagnostics. | Reproducible trace/test plus field or controlled-lab evidence against project-owned thresholds. | Major when critical journey or SLO is breached; Critical if consequential harm occurs. |
| Poor usability, cognitive overload, or inaccessible journey | Can intended and edge-case users complete the task accurately and safely? | Map user goal and context; simplify choices; make states/errors clear; provide recovery; test keyboard/screen reader, zoom, and assistive contexts; perform task-based usability testing. | Task-success/error data, accessibility evidence, and qualitative observations are recorded by relevant user/context segment. | Critical/Major for exclusion of core users or significant harmful error; otherwise context-based. |
| Weak risk register or unstated assumptions | Which assumptions, human impacts, detection difficulty, or residual risks could invalidate the decision? | Give each risk a stable ID, probability/likelihood, impact including human impact, detectability, owner, mitigation, residual risk, and escalation trigger; state assumptions and constraints that would invalidate key decisions. | Risks have accountable owners, actionable mitigation, stated assumptions, and a documented residual-risk decision. | Major when an unowned assumption affects a critical path; Critical/Major according to likely harm or exposure. |
| Missing or shallow user context/personas | Which primary, edge, situational, or excluded users are not represented by the current happy path? | Describe goals, pain points, context, device, literacy, time pressure, accessibility needs, constraints, and user-visible success criteria; mark out-of-scope groups explicitly and justify. | Requirements and tests cover relevant user contexts, or exclusions are explicit and approved. | Major if a required population is likely to be excluded or repeatedly fails. |
| Poor structure, discoverability, or oversized skill instructions | Can the intended reader or agent locate the correct rule quickly without losing essential context? | Use clear heading hierarchy, stable IDs, navigation/glossary where useful, concise executive summary for long artifacts, and extract detailed material into linked references; avoid duplicating canonical guidance. | Representative users/agents can locate required guidance; links resolve; key rules are not contradicted or hidden. | Major if structure causes a material implementation or safety rule to be missed; otherwise Minor. |
| Missing skill lifecycle controls or feedback cadence | Are learned failures captured after real use, and can a skill change be traced to a reviewed version? | Set semantic version, last-reviewed date, migration notes for contract-breaking changes, owner/reviewer and regression tests; capture first-use defects promptly (e.g., within 24–48 hours when practical) and revalidate after each change batch. Never label a skill exceptional while Critical findings remain open. | Version and change rationale are traceable; regression cases reproduce previous failures; set/member checks pass; residual risk is recorded. | Block release for unresolved Critical findings or breaking contract changes without migration. |
| Weak personas or human-factors assumptions | Is the assumed user/context supported by evidence? | Identify primary, extreme, and situational users; label assumptions; plan research or walkthrough; add inclusion and comfort/trust considerations. | Assumptions and validation method are explicit; evidence changes design/requirements where needed. | Major if assumption excludes a required user group or causes repeated failure. |
| Trigger false positives / misses | Which positive scenario failed to activate or unrelated scenario activated? | Refresh concrete positive/negative utterance set; revise description with distinguishing context and trigger terms; rerun test set. | ≥90% true positives and ≤10% false positives on a documented set of at least five positive and five negative prompts, or a justified larger design. | Block skill release if declared trigger acceptance criteria fail. |
| Missing/unmeasurable skill metrics | Does each metric have a definition, target, data source, sample, and window? | Add the five canonical dimensions: trigger performance, task completion, context-token efficiency, time-to-working-skill, residual defect density. Make each separately testable. | The required metrics are explicit, measurable, and validated against actual observations rather than presence-only checks. | Block skill release if a required dimension or mandatory measurement definition is missing. |
| Structural or semantic validator regression | Does the validator return non-zero for a known-invalid fixture? | Add a minimal invalid fixture for the failed gate and a matching valid fixture; ensure mandatory checks fail closed and failure messages identify the gate. | Positive fixtures exit 0; negative fixtures exit non-zero for the expected reason; complete suite passes. | Block merge for validator/test regressions. |
| Script is untested or has unsafe side effects | What input, permission, file/network access, or failure mode is uncontrolled? | Add usage/side-effect comments, argument/type checks, temporary output/atomic writes, bounds, error handling, and positive/negative tests. | Offline tests prove expected output, fail-closed behavior, and absence of unintended mutation/network execution. | Critical if secrets, privileged actions, or untrusted code are exposed. |
| Skill contract or composition conflict | Are dependencies explicit and acyclic; do members agree on schema/version/ownership? | Declare member versions, dependency DAG, provided/required contracts, loading order, conflict strategy, and migration policy. Use one shared contract source. | Manifest and contract validation pass; integration tests cover each declared interface. | Block set release on unresolved required dependency or contract conflict. |
| Human-factors guidance missing from a skill | Does the skill account for author/user cognitive load, error communication, inclusivity, and recovery? | Add relevant human-factors instructions, examples, failure-state guidance, and acceptance tests. | Representative tasks are assessed; error recovery and accessibility expectations are demonstrable. | Major for critical task failure, exclusion, or unsafe interaction. |
| Residual defect, no ownership, or issue repeatedly reopens | Was the root cause treated, or only the symptom? | Assign owner and next action; reproduce reopened issue; revisit root cause and previous acceptance criterion; add recurring failure as a regression fixture. | Issue remains closed through a defined observation window and regression suite passes. | Escalate repeated Critical/Major recurrence to the responsible engineering/review lead. |

## Cross-Skill Feedback Rule
An audit finding should trigger a skill-spec evaluation only when (a) it is open/in progress and explicitly indicates a suspected skill-level gap, or (b) the same pattern recurs in at least two distinct audit observations backed by unique `recurrence_observation_ids` (including the current audit ID) whose count matches `recurrence_count`. A count without traceable observation IDs is not recurrence evidence. A one-off project issue should remain project remediation unless evidence supports a skill gap. Follow `shared/references/feedback-loop.md` and the contracts in `shared/contracts/` for routing. The processor generates a request; it never changes a live skill automatically.

## Root-Cause to Verification Trace
For every Critical/Major remediation, preserve this compact trace:
`finding ID → evidence → root cause → chosen change → acceptance criterion → test/measurement result → reviewer/decision → residual risk`.
For skill-level changes, additionally map:
`finding category → target skill → trigger/instruction/reference/contract affected → regression fixture → metric result`.

## Measurement and Anti-Gaming
Track resolution time by severity/category, reopened rate, recurrence by root cause, and proportion of changes verified against their acceptance criteria. Do not optimize time-to-resolution alone: rapid closure without a reproduced fix, regression test, or user-impact check is not successful remediation. For production deployment incidents, preserve the exact scope of the chosen metric; do not silently equate generic incident MTTR with DORA's failed-deployment recovery-time definition.


## Evidence State and Severity Calibration

Keep evidence state and severity as separate dimensions. Use `Verified`, `Inference`, `Unknown/Untested`, `Contradicted`, or `Not applicable` for the evidence state, and record source location, version/as-of date, verification method, and confidence basis for material claims. Missing or inaccessible material is not proof that a control is absent and must never be treated as a pass. Raise severity only when a requirement, inspected state, corroborating evidence, or explicit conditional consequence analysis supports the impact/exposure. When a mandatory control is unverified, say exactly that and express the severity as a conditional risk if necessary; do not convert uncertainty into a factual defect.
